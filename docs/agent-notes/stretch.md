# Exact B-rep export for .ifc and .3dm (notes)

## .ifc (built)
- IfcOpenShell 0.9.0.post1 wheels are `py310-none` per platform (macOS x86_64 and arm64, manylinux aarch64 and x86_64, Windows); they work on Python 3.13. They carry NO Python OCC bindings (`ifcopenshell.geom.has_occ` is False), so there is no route from an OCP shape through the IFC library itself.
- Built instead: `core/src/pliable/filesifcexact.py` writes IfcAdvancedBrep ourselves from OCP data with the IFC library already in use (no new dependency). Analytic planes, cylinders, spheres, tori; lines, circles, ellipses; everything else becomes a B-spline (rational where the weights differ; periodic ones cut open so knots are clamped). IFC4 has no cone: cones are written as a rational B-spline of four quarter arcs (the kernel's own 3-arc conversion is meshed wrongly by the IFC reader: bulged cones).
- Fallback to the faceted body per solid when the exact writer raises: faces with a degenerate edge (poles, e.g. a full sphere; the reader drops such a face), solids with more than one shell.
- Import is unchanged (default meshing); exact bodies re-import with about 1 percent volume error on curved parts, so those round-trip tests use a 2 percent tolerance and the exact checks read the file back with a fine deflection inside the tests.
- Checked by reading the files back through the IFC geometry iterator at a fine deflection: signed volume matches the kernel volume within 0.2 percent for box, cylinder, filleted bracket with a hole, cone (both directions), torus, loft, revolved profile, extruded spline; the sign is positive so the faces point outward.
- Import of an exact IFC body still goes through triangles (the reader sews meshes); exact import is not part of this row.

## .3dm (not built; needs a decision)
- rhino3dm 8.35.0 (the only Python openNURBS wheel with B-reps) has read-only `BrepFaceList`, `BrepEdgeList`, `BrepTrimList`, `BrepLoopList`, `BrepVertexList` (no Add). Constructors cover only boxes, spheres, cylinders, cones, one surface, a planar trimmed face, a revolved surface and a mesh (`CreateFromMesh`, planar triangles only): no general trimmed B-rep and no join.
- py3dm 0.1.1 (nanobind openNURBS bindings, wheels cp313 for Windows, macOS, Linux x86_64; about 1.6 to 3.7 MB) exposes only points, line curves, meshes, layers: no B-rep classes at all. No other PyPI package ("opennurbs", "pyopennurbs") exists. No route through a new library.
- Remaining route without a dependency: write the openNURBS binary of an `ON_Brep` ourselves and hand it to `rhino3dm.Brep.Decode({"version": 10000, "archive3dm": 60, "opennurbs": ..., "data": base64})`, then `File3dm.Objects.AddBrep`. `Brep.Decode(brep.Encode())` round-trips and `IsValid` would validate our bytes. The data is a class chunk (0x00027ffa: class uuid chunk, data chunk, end mark) holding ON_Brep's arrays of 2D curves, 3D curves, surfaces (NURBS surface objects), vertices, edges, trims, loops and faces. The layout is not documented in the wheel; it must be reverse-engineered from `Brep.Encode()` of small shapes (a box encodes to 12 KB). Estimate: a multi-hour, risky task (NURBS curve and surface chunk formats plus trim and loop records, with CRCs), but no new dependency and fully checkable with `IsValid` and our own 3dm import.

3dm decision (coordinator): keep the mesh export; no direct writer.
